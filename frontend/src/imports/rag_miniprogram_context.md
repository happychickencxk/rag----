# 企业知识库 RAG 问答系统：微信小程序端项目压缩说明

> 用途：本文件用于喂给 Figma Make / Galileo / Uizard / Motiff 等 UI 生成工具，帮助其理解“企业知识库 RAG 问答系统”的微信小程序端产品背景、页面范围、核心流程和 UI 约束。
> 目标：生成微信小程序端高保真原型，而不是 Web 管理后台。

---

## 1. 项目名称

企业知识库 RAG 问答系统

---

## 2. 项目一句话定位

本项目是一个面向企业内部知识服务场景的 RAG 问答系统。它把企业制度、产品手册、技术文档、售后规范、培训资料、FAQ 等文档转化为可检索知识库，并通过大语言模型生成带引用来源的可信回答。

微信小程序端的定位不是后台管理系统，而是“轻量问答入口”。用户通过小程序完成：

选择知识库 → 输入问题 → 查看 AI 回答 → 查看引用来源 → 继续追问 → 点赞 / 点踩 / 提交纠错

---

## 3. 项目要解决的问题

企业内部知识通常存在以下问题：

1. 文档来源分散：资料散落在文件夹、网盘、IM 群、在线文档、历史工单中。
2. 版本复杂：同一制度、产品手册、售后规范可能存在多个版本。
3. 检索效率低：员工和客服需要反复翻文档，查找成本高。
4. 回答缺少依据：普通聊天机器人可能给出没有来源的回答。
5. 大模型容易幻觉：模型可能生成与企业真实资料不一致的内容。
6. 权限需要控制：不同部门、角色、用户只能访问授权知识。
7. 低质量问答需要沉淀：低命中、无引用、点踩、纠错要进入知识维护闭环。

---

## 4. 小程序端核心用户

### 4.1 普通员工

使用场景：
- 查询企业制度、请假流程、报销流程、办公规范、内部 FAQ。
- 通过自然语言提问，快速获得带引用来源的答案。

典型问题：
- 试用期请假是否影响转正？
- 如何申请远程办公？
- 报销发票有什么要求？

### 4.2 客服人员

使用场景：
- 查询售后规范、退换货政策、产品常见问题。
- 快速复制标准答复给客户。
- 遇到未命中问题时提交“需补充知识”。

典型问题：
- 售后退换货流程是什么？
- 超过 7 天还能退货吗？
- 客户安装失败应该怎么排查？

### 4.3 技术支持 / 外勤人员

使用场景：
- 查询产品安装手册、故障排查步骤、技术文档。
- 在移动场景快速查看引用依据。

典型问题：
- 产品安装失败如何排查？
- 某型号设备无法联网应该检查哪些步骤？
- 固件升级失败怎么办？

## 5. 小程序端核心业务流程

### 5.1 问答流程

1. 用户打开微信小程序。
2. 用户选择当前知识库，如“人事制度库”“产品资料库”“售后知识库”“研发技术库”。
3. 用户在底部输入框输入自然语言问题。
4. 系统读取用户身份、部门、角色和当前知识库。
5. 系统按权限过滤用户可访问的文档片段。
6. 系统对用户问题进行向量化。
7. 系统从知识库中召回相关知识片段。
8. 系统使用 Rerank 对候选片段重新排序。
9. 系统判断是否有足够依据。
10. 如果有依据，系统调用 LLM 生成回答。
11. 小程序展示 AI 回答、引用来源、原文片段和反馈入口。
12. 用户可以继续追问、查看引用详情、点赞、点踩、复制答案或提交纠错。

### 5.2 引用溯源流程

1. 用户在 AI 回答下方看到引用来源卡片。
2. 引用卡片显示文档名、章节路径、原文片段摘要、相似度 / Rerank 分数。
3. 用户点击引用卡片进入引用详情页。
4. 引用详情页展示文档名、所属知识库、章节路径、更新时间、原文片段、命中句高亮。
5. 如果用户无权查看完整原文，则显示权限提示，只展示允许范围内的摘要。

### 5.3 反馈纠错流程

1. 用户对回答点击“点踩”“无引用”“引用错误”“答案不完整”等反馈按钮。
2. 系统进入反馈纠错页。
3. 用户选择反馈类型并补充说明。
4. 反馈进入知识维护闭环，供知识库管理员或部门知识负责人处理。
5. 反馈状态后续可流转为：待处理 → 处理中 → 已修复 / 已忽略。

## 6. 小程序端推荐页面

### 页面 1：问答首页

用途：
- 小程序核心页面，用户进入后可以直接提问。

页面结构：
- 顶部 NavBar：标题“企业知识库助手”，右侧有历史入口和更多按钮。
- 知识库选择器：显示当前知识库，可点击切换。
- 欢迎卡片：说明系统可以基于企业知识库回答，并提供引用来源。
- 示例问题 chips：展示 3~4 个常见问题。
- 对话消息流：用户问题气泡、AI 回答卡片、流式输出 loading 状态。
- 引用来源折叠卡片：AI 回答下方展示最多 3 条引用。
- 底部固定输入栏：多行输入框、语音按钮、发送按钮、附件/更多按钮。

核心要求：
- 页面必须突出“选择知识库 → 输入问题 → AI 回答 → 引用来源 → 反馈”。
- 引用来源不能被弱化。
- 底部输入栏要固定在页面底部，适配键盘弹出。

### 页面 2：知识库选择页

用途：
- 用户选择查询范围。

页面结构：
- 顶部标题“选择知识库”。
- 搜索框：搜索知识库名称。
- 知识库列表：
  - 人事制度库
  - 产品资料库
  - 售后知识库
  - 研发技术库
  - 培训资料库
  - 企业 FAQ
- 每个知识库 cell 包含：名称、描述、所属部门、更新时间、权限状态。
- 当前选中知识库显示蓝色勾选状态。
- 无权限知识库置灰，显示“无访问权限”。

### 页面 3：引用来源详情页

用途：
- 让用户核验答案依据，降低大模型幻觉风险。

页面结构：
- 顶部标题“引用来源”。
- 文档信息卡：文档名、所属知识库、章节路径、更新时间、权限标签。
- 分数信息：相似度分数、Rerank 分数。
- 原文片段区域：展示命中片段，命中句高亮，长文本可折叠展开。
- 操作按钮：复制引用、查看上下文、反馈引用错误。
- 权限提示：无权查看完整原文时显示说明。

### 页面 4：历史会话页

用途：
- 用户找回历史问答。

页面结构：
- 顶部搜索框：搜索历史问题。
- 时间分组：今天、昨天、近 7 天、更早。
- 会话列表 cell：
  - 会话标题
  - 所属知识库
  - 最近一条回答摘要
  - 消息数量
  - 更新时间
- 支持删除或更多操作。
- 空状态：暂无历史会话，引导用户去提问。

### 页面 5：反馈纠错页

用途：
- 用户对低质量回答提交反馈。

页面结构：
- 原问题摘要。
- AI 回答摘要。
- 引用来源摘要。
- 反馈类型选择：
  - 答案不正确
  - 引用错误
  - 没有引用
  - 答案不完整
  - 无权限但展示了敏感内容
  - 其他
- 补充说明文本框。
- 提交按钮。
- 提交成功状态：提示“反馈已提交，知识库负责人将进行处理。”

### 页面 6：我的页

用途：
- 展示用户身份、权限范围和个人设置。

页面结构：
- 用户头像、姓名、部门、角色。
- 我的知识库权限。
- 我的反馈记录。
- 最近使用的知识库。
- 设置项：
  - 清空历史会话
  - 消息通知
  - 帮助与反馈
  - 关于系统
- 退出登录按钮。

### 页面 7：异常状态组件集合

必须包含：
1. Loading：AI 正在检索企业知识库...
2. Streaming：正在基于知识库生成回答...
3. NoEvidence：当前知识库未找到足够依据，建议换一种问法或切换知识库。
4. LowConfidence：该回答置信度较低，请结合引用来源人工确认。
5. NoPermission：你无权访问该知识库或文档片段。
6. ModelTimeout：模型服务响应超时，可稍后重试。
7. SensitiveBlocked：问题包含敏感内容，系统已拦截。
8. EmptyHistory：暂无历史会话。
9. EmptyKnowledgeBase：暂无可访问知识库。

## 7. 小程序端不应该重点设计的内容

以下内容属于 Web 管理后台或系统管理端，不应作为小程序端主界面：

1. 完整文档上传与批量管理。
2. 文档解析流水线详情。
3. Embedding / Rerank / LLM 模型配置。
4. TopK、TopN、chunk_size、chunk_overlap、similarity_threshold 等参数配置。
5. 审计日志大表格。
6. 权限管理后台。
7. 大型统计看板。
8. 数据库 ER 图、部署架构、服务监控。
9. 多列 Dashboard 布局。
10. Web 端左侧导航栏和复杂筛选器。

小程序端只保留“轻量问答、引用查看、历史会话、反馈纠错、个人权限展示”。

## 8. 视觉风格建议

整体风格：
- 微信小程序原生体验。
- WeUI 风格。
- 企业工具类产品气质。
- 简洁、克制、可信。
- 单列布局，避免 Web 后台感。

色彩建议：
- 背景：#F7F8FA
- 卡片：#FFFFFF
- 主色：企业蓝 #1677FF 或微信蓝
- 成功色：绿色，用于有依据 / 检索成功
- 警告色：橙色，用于低置信度 / 无依据
- 错误色：红色，用于无权限 / 模型超时 / 敏感词拦截
- 分割线：浅灰色

字体建议：
- 页面标题：18px
- 模块标题：16px
- 正文：14px
- 辅助文字：12px

圆角建议：
- 普通卡片：12px
- 消息气泡：12~16px
- 按钮：8~12px
- 标签：6px

间距建议：
- 使用 8px spacing system。
- 小程序中可按 16rpx 基准理解。
- 常用间距：8px / 12px / 16px / 24px。

## 10. 交互要求

1. 不使用 hover。
2. 使用点击态、按压态、loading 态。
3. 引用来源在问答页中以折叠卡片展示。
4. 点击引用来源后进入引用详情页或底部弹层。
5. 反馈操作可以使用底部 ActionSheet。
6. 知识库选择可以使用列表页或 bottom sheet。
7. 底部输入栏固定在页面底部。
8. 输入框需要适配键盘弹出。
9. 流式输出时显示“正在基于知识库生成回答”。
10. 无依据、无权限、模型超时等状态必须有明确提示。
11. 所有重要回答必须尽量展示引用来源。
12. 如果没有检索依据，不应生成强结论式回答，应提示未找到足够依据。

## 11. Figma Make 生成目标

目标平台：
- 微信小程序
- 企业微信小程序
- 移动端尺寸 375×812
- 750rpx 设计思维

输出目标：
- 高保真小程序 UI 原型
- 页面结构清晰
- 图层可编辑
- 组件可复用
- 适合后续转为 WXML + WXSS
- 适合参考 WeUI / TDesign MiniProgram / Vant Weapp 组件实现

---

## 12. 给 Figma Make 的重点提醒

请确保最终设计满足：

1. 像微信小程序，不像 Web 后台。
2. 主路径是问答，不是管理。
3. 引用来源必须清楚。
4. 权限状态必须清楚。
5. 异常状态必须完整。
6. 不使用复杂表格、大型图表、左侧导航、多列 Dashboard。
7. 不直接复制任何现有品牌。
8. 不把文本、图标、卡片合成不可编辑图片。
9. 所有组件保持可复用，命名清晰。
10. 适合微信小程序前端实现。
